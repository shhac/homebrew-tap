# Homebrew Formula Management

## 0. Check How the Formula Is Published

Most formulae here are generated by a release pipeline, which rewrites the whole file on every release. Check which kind you have before editing anything:

| Formulae | Published by |
|----------|--------------|
| All `agent-*`, `crew-*`, `g2g`, `git-wt`, `lin` | `.github/workflows/go-release.yml`, called from the tool repo's `release.yml` on a `v*` tag |
| `git-hunk`, `toss` | The tool repo's own `release.yml` (a heredoc in its "Generate formula" step) |
| `prtea`, `Casks/grotto.rb` | Hand-maintained in this repo |

To confirm for a given tool:
```bash
gh api repos/shhac/<name>/contents/.github/workflows/release.yml --jq .content | base64 -d | grep -E 'go-release|TAP_DEPLOY_KEY'
```

### What happens when a pipeline publishes

On a `v*` tag push in the tool repo, the pipeline builds the release archives, creates the GitHub Release, writes `Formula/<name>.rb` from its template, and pushes it to `main` here as `github-actions[bot]` with the message `<name> <version>`. It needs no help from this repo, which means:

- **Version bumps need nothing here.** Don't bump a pipeline formula by hand; tag a release in the tool repo instead. A hand bump gets overwritten, or conflicts with the bot's push.
- **Hand fixes to a pipeline formula only last until the next release.** Make the fix at its source as well: the `with:` inputs in the tool's `release.yml` (desc, help text, license, binary name), the template in `go-release.yml` (layout for every Go tool), or the heredoc in a Zig tool's `release.yml`. A hand fix in this repo is still useful as a stopgap until the next release.
- **New Go CLIs are added from the tool repo**, not here. The first tagged release creates the formula. See "Publishing with go-release.yml" in `AGENTS.md` for the caller workflow, the `homebrew-tap` environment and the `TAP_DEPLOY_KEY` secret. Then add the formula to the `README.md` table.
- **`go-release.yml` checks `desc` against Homebrew's style rules** before publishing. A desc that `brew style` would rewrite (an article first, a lowercase first word, a trailing full stop, more than 80 characters) fails the release.
- **Don't run the "Generate + push Homebrew formula" step locally** to preview output. It clones this tap and pushes for real. Copy only the heredoc into a scratch script.

Everything below is for hand-maintained formulae, or for stopgap fixes to generated ones.

## Adding a New Formula by Hand

### 1. Gather Information

Check if formula already exists:
```bash
ls Formula/<name>.rb 2>/dev/null && echo "Formula exists - use update workflow"
```

Ask user for:
- Tool name and GitHub repository URL
- Current version to publish
- Brief description (under 80 chars)
- License type (MIT, Apache-2.0, GPL-3.0, etc.)

Determine binary distribution strategy:
- **Pre-built binaries** (recommended): Use when GitHub releases include platform-specific archives
- **Build from source**: Use when no pre-built binaries exist or only source tarballs are published

### 2. Get Download URLs and Checksums

For pre-built binaries, identify release assets for each platform:
- macOS ARM64 (Apple Silicon)
- macOS x86_64 (Intel)
- Linux ARM64
- Linux x86_64

Calculate SHA256 for each archive:
```bash
curl -sL "<url>" | shasum -a 256
```

For source builds, get the source tarball URL and hash:
```bash
curl -sL "https://github.com/<owner>/<repo>/archive/refs/tags/v<version>.tar.gz" | shasum -a 256
```

Inspect archive structure to determine install method:
```bash
curl -sL "<url>" -o "$TMPDIR/archive.tar.gz" && tar -tzf "$TMPDIR/archive.tar.gz" | head -20
```

### 3. Create Formula File

Create `Formula/<name>.rb` using patterns from `references/formula-reference.md`.

Formula requirements:
- Class name: CamelCase version of tool name
- Include `desc`, `homepage`, `license`
- No `version` stanza when the URLs contain the version. Homebrew reads it from them, and `brew audit --strict` flags an explicit one as redundant.
- Platform-specific blocks for multi-arch binaries
- `install` method to place binary in `bin`
- `test` block with meaningful verification

### 4. Validate Formula

Ensure file permissions are correct:
```bash
chmod a+r Formula/<name>.rb
```

Run style check (this one works on a path):
```bash
brew style Formula/<name>.rb
```

`brew audit` and `brew test` reject file paths ("Calling `brew audit [path ...]` is disabled", "Homebrew requires formulae to be in a tap"). Copy the formula into the tapped clone and work by name:
```bash
TAP_PATH=$(brew --repo shhac/tap)
cp Formula/<name>.rb "$TAP_PATH/Formula/"
brew audit --strict shhac/tap/<name>
brew install shhac/tap/<name>
brew test shhac/tap/<name>
```

`brew audit --strict --online` additionally checks the URLs resolve, so it only passes once the release exists.

After testing, restore the tapped clone:
```bash
git -C "$TAP_PATH" checkout -- Formula/<name>.rb 2>/dev/null || rm "$TAP_PATH/Formula/<name>.rb"
brew uninstall shhac/tap/<name>   # only if it was not installed before
```

Fix any issues before proceeding.

### 5. Update README and Commit

Add a row to the `README.md` formula table, using the formula's `desc` verbatim.

Commit with message: `<name> <version>` (e.g. `prtea 0.6.0`). This matches what the release pipelines push.

## Updating an Existing Formula by Hand

For a pipeline-published formula, read section 0 first: the right fix is usually in the tool repo.

### 1. Update URLs and Checksums

Edit `Formula/<name>.rb`:
- Update all download URLs with new version
- Update all `sha256` checksums
- Update `version` only for a cask, or for a formula whose URLs don't contain the version

### 2. Update Test Block

Ensure test block references correct version string if it checks `--version` output.

### 3. Validate and Commit

Run the same validation sequence as new formulas.

Commit message:
- Version bump: `<name> <version>`
- Any other fix: a conventional commit, e.g. `fix[<name>]: ...` or `fix[tap]: ...` when it spans formulae

## Renaming a Formula

In one commit: `git mv Formula/<old>.rb Formula/<new>.rb`, rename the class, and add `"<old>": "<new>"` to `formula_renames.json`. Homebrew uses the mapping to migrate existing installs. Leave URLs and checksums for the current release untouched; the next release regenerates them under the new name. Commit as `chore: rename the <old> formula to <new>`, and add the rename to the README's renamed-formulas table.

## Common Issues

### SHA256 Mismatch
Re-download and recalculate: `curl -sL "<url>" | shasum -a 256`

### Binary Not Found in Archive
Check archive structure: `tar -tzf <archive>.tar.gz`
Update `install` method to match actual binary path.

### Style Violations
Run `brew style --fix Formula/<name>.rb` for auto-fixable issues. For a pipeline formula, fix the generator too, or the next release reintroduces the offence.

### Test Failures
- Verify binary runs: `./path/to/binary --version`
- Check test regex matches actual output format
- Use `--seed` or similar flags for deterministic test output
- **stderr vs stdout**: Some CLIs output `--version` and `--help` to stderr. Use `2>&1` in test assertions:
  ```ruby
  assert_match "version", shell_output("#{bin}/tool --version 2>&1")
  ```

### Shell Integration
For tools requiring shell aliases/functions, use `def caveats` to inform users (Homebrew convention is NOT to auto-modify shell configs):
```ruby
def caveats
  <<~EOS
    To enable shell integration, add to your shell config:

      eval "$(tool-name alias cmd)"
  EOS
end
```

For shell completions, prefer `generate_completions_from_executable(bin/"tool", "completion")` when the tool can print its own completion scripts.
