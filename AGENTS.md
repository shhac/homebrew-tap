# AGENTS.md

Guidance for coding agents working in this repository.

## Overview

Personal Homebrew tap for distributing custom CLI tools. Tap name: `shhac/tap`.

- `Formula/` holds the formulae and `Casks/` holds the casks.
- `formula_renames.json` maps old formula names to new ones so existing installs migrate.
- `.github/workflows/go-release.yml` is a reusable release workflow that the Go CLI repos call.
- `scripts/download-stats.sh` counts release downloads per tool, which is the closest thing to install analytics a third-party tap has.
- `.agents/skills/homebrew-formula/` is the step-by-step skill for adding and updating formulae. `.claude/skills/homebrew-formula` is a symlink to it.

## How each formula is published

Most formulae are generated by a release pipeline that rewrites the whole file on every release. A hand-edit to a generated formula survives only until that tool's next release, so fix the source instead.

| Formulae | Published by | Where to change it |
|----------|--------------|--------------------|
| All `agent-*`, `crew-*`, `g2g`, `git-wt`, `lin` | `go-release.yml` in this repo, called from each tool's `release.yml` | The tool repo's `release.yml` inputs (desc, help text), or the template in `go-release.yml` (layout for every Go tool) |
| `git-hunk`, `toss` | Each tool repo's own `release.yml` (Zig builds) | The heredoc in that repo's `release.yml` |
| `prtea`, `Casks/grotto.rb` | Nobody: committed by hand | This repo |

## Publishing with go-release.yml (Go CLIs)

A tool repo releases by pushing a `v*` tag. The workflow then cross-builds darwin/linux (arm64 and amd64) plus windows/amd64, creates the GitHub Release, writes `Formula/<name>.rb`, and pushes it straight to `main` here as `github-actions[bot]`.

To add a new Go CLI:

1. In the tool repo, add `.github/workflows/release.yml`:

   ```yaml
   name: Release

   on:
     push:
       tags:
         - 'v*'

   jobs:
     release:
       uses: shhac/homebrew-tap/.github/workflows/go-release.yml@main
       permissions:
         contents: write
       secrets: inherit
       with:
         name: agent-example             # release assets, formula file, github.com/shhac/<name>
         desc: "Example CLI for AI agents"
         formula_class: AgentExample
         help_match: "Example CLI"       # substring the formula test expects in `<name> --help`
   ```

   Optional inputs: `cmd_path` (defaults to `./cmd/<name>`), `installed_binary_name` (when the installed command differs from `name`), and `license` (detected from `LICENSE` when omitted).

2. The binary must print the version it was built with (`-X main.version` is set) for `--version`, and must support `completion bash|zsh|fish`. The generated test asserts all three.
3. In the tool repo, create a `homebrew-tap` environment that only `v*` tags can deploy to, and add a `TAP_DEPLOY_KEY` secret to it. The secret is the private half of a write deploy key on `shhac/homebrew-tap`. Without the secret, the release still publishes and only the tap update is skipped.
4. Tag and push: `git tag v0.1.0 && git push origin v0.1.0`. The first release creates the formula, so nothing needs adding here first. Then add the formula to the README table.

The workflow checks `desc` against Homebrew's style rules before it publishes anything. If the desc fails those rules, the release stops there.

Don't run the workflow's "Generate + push Homebrew formula" step locally to preview a formula. It clones this tap and pushes for real. Copy just the heredoc into a scratch script instead.

## Adding or updating a formula by hand

Do this for tools without a release pipeline, or to fix a formula before its next release.

1. Create or edit `Formula/<name>.rb`, following `Formula/toss.rb`:
   - Use `on_macos`/`on_linux` blocks, each containing `on_arm`/`on_intel`, with a `url` and `sha256` per platform.
   - Leave out the `version` stanza. Homebrew reads the version from the URLs, and `brew audit` flags a matching explicit version as redundant.
   - Add a `test` block that checks `--version` output and at least one real behaviour.
2. Get checksums with `curl -sL <url> | shasum -a 256`.
3. Validate the formula. `brew audit` and `brew test` only accept a formula that is in a tap. Given a file path, they reject it ("Calling `brew audit [path ...]` is disabled", "Homebrew requires formulae to be in a tap"). So copy the formula into the tapped clone and work by name:

   ```bash
   brew style Formula/<name>.rb                 # style/lint works on the path
   cp Formula/<name>.rb "$(brew --repo shhac/tap)/Formula/"
   brew audit --strict shhac/tap/<name>
   brew install shhac/tap/<name> && brew test shhac/tap/<name>
   ```

   Afterwards, put the tapped clone back: `git -C "$(brew --repo shhac/tap)" checkout -- Formula/<name>.rb` for an existing formula, or `rm` the copy for a new one.

4. If the tool is published by a pipeline, make the same fix there, or the next release undoes it.

## Renaming a formula

In one commit, rename `Formula/<old>.rb` to `Formula/<new>.rb`, rename the class, and add `"<old>": "<new>"` to `formula_renames.json`. The mapping is how Homebrew moves existing installs over. Without it, an installed keg silently stops getting updates. Leave the URLs and checksums alone: they describe the release that already exists, and the next release regenerates them under the new name.

## Commit messages

- Adding or bumping a formula: `<name> <version>`, e.g. `agent-slack 0.49.1`. The release pipelines use this format, so hand-made bumps should match.
- Anything else: conventional commits, e.g. `fix[tap]: ...`, `chore: rename the gt2gh formula to g2g`, `docs: ...`.

## Commands

```bash
brew tap shhac/tap
brew install shhac/tap/toss
brew style Formula/toss.rb
brew audit --strict shhac/tap/toss
brew test shhac/tap/toss
scripts/download-stats.sh --min-live 2 --sort median
```
